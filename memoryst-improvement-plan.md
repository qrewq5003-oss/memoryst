# План доработки memoryst: контекстное извлечение, консолидация, raw fallback

## Цель

Заменить построчную regex-классификацию памяти на извлечение по сцене целиком,
улучшить консолидацию, добавить возможность достать детали из сырой истории чата,
когда консолидация их упустила.

Хранилище — локальное (SQLite), извлечение — через внешний LLM API (как сейчас, `llm_client.py`).

---

## Этап 0 — Уточнения, закрытые перед началом работы

- Fallback на raw-историю триггерится **двумя способами**: вручную по запросу пользователя
  ("дай детали") и автоматически по confidence score от retrieval.
- Текущий технический долг чистится **до** написания нового pipeline, не после.
- Последние 4 сообщения **именно чата** (не OOC, не системные, не служебные) не попадают
  в постоянную raw-таблицу — хранятся как "горячий буфер" вне базы, чтобы их можно было
  свайпнуть/удалить без последствий для консолидированной памяти. В raw-таблицу попадают
  только сообщения, которые "остыли" (перестали быть в последних 4).
- ID сообщений должны быть устойчивыми (UUID при первой записи), не порядковым индексом —
  иначе свайп/редактирование где-то в середине истории ломает ссылки из memory на raw.

## Этап 1 — Чистка текущего долга (делать первым, без этого новый pipeline будет тройной работой)

- **[ПРАВКА от 2026-07-01, проверено по коду]** Судьба `llm_extractor.py` / `/memory/scene`

  в веб-UI (`app/templates/_tools.html` + `_scripts.html`), которая дёргает

  **Новая рекомендация: не удалять.** Вместо этого на Этапе 3 переиспользовать
  `extract_with_llm`/`build_scene_text` как основу для автоматического extraction по сцене
  (заменить хрупкий `re.search(r"\{[^{}]*\}")` на structured output), а ручной UI-эндпоинт
  `/memory/scene` оставить как есть или развернуть в сторону того же общего extraction-пути.

### 1.2 Вынести retrieval-веса в конфиг
- 24 магические константы в `retrieve_service.py` (`KEYWORD_WEIGHT`, `SEMANTIC_BOOST` и т.д.)
  вынести в YAML/JSON конфиг с версионированием.
- Подключить существующий `scripts/run_retrieval_eval.py` как обязательный шаг в CI

### 1.3 Безопасность
- `API_KEY` по умолчанию пустая строка = auth отключена. Если `APP_HOST` не `127.0.0.1`,
  требовать непустой ключ при старте (явный fail-fast, а не молчаливая дыра).
- **[ПРАВКА от 2026-07-01, проверено по коду]** Хуже, чем предполагалось: `APP_HOST` в
  `app/config.py` по умолчанию равен **`0.0.0.0`**, не `127.0.0.1`. То есть сервер уже
  по дефолту слушает все интерфейсы без обязательного ключа — fail-fast здесь не
  опциональное улучшение, а закрытие дыры, которая активна из коробки.
- **[ПРАВКА]** `google_keys.json` как файла в репозитории сейчас нет — ключи передаются
  через `.env` (`GOOGLE_API_KEYS`). Но `app/services/vector_store.py:24` определяет
  `KEYS_FILE = data/google_keys.json` и **пишет** туда ключи при ротации
  (`KEYS_FILE.write_text(...)`). Текущий `.gitignore` содержит только `data/memory.db` —
  ни `.env`, ни `data/chromadb/`, ни будущий `data/google_keys.json` не игнорируются.
  Добавить в `.gitignore`: `.env`, `data/google_keys.json`, `data/chromadb/` —
  до того, как ротация ключей создаст этот файл на диске у кого-то из разработчиков.

### 1.4 Async-проблема в vector_store.py
- `_call_embed` использует синхронный `httpx.post` внутри асинхронного FastAPI-стека —
  блокирует event loop. Заменить на `httpx.AsyncClient`.
- **[ПРАВКА от 2026-07-01, проверено по коду]** Уточнение, где это реально бьёт: почти все
  роуты в `memory_api.py`/`ui.py` — синхронные `def`, FastAPI сам уносит их в threadpool,
  для них блокировка event loop не критична. Единственный `async def`-роут —
  `ui_backfill_file` (`app/routes/ui.py:574`) — импортирует `vector_store` и идёт по тому
  же store-пути, что и `_call_embed`. Значит при загрузке файла бэкфилла синхронный
  HTTP-вызов к Google embeddings API выполняется прямо в event loop и блокирует весь сервер
  на время обработки файла (потенциально много сообщений подряд). Это не гипотетический
  риск, а конкретный горячий путь — приоритизировать фикс здесь.

## Этап 2 — Raw-хранилище сообщений (новая подсистема, не существует сейчас)

Проверено: `app/repositories/` содержит только `memory_repo.py`. Таблицы сырых сообщений
чата нет вообще — это нужно строить с нуля.

### 2.1 Схема таблицы
```sql
CREATE TABLE chat_messages (
    id TEXT PRIMARY KEY,           -- UUID, не порядковый индекс
    chat_id TEXT NOT NULL,
    character_id TEXT NOT NULL,
    role TEXT NOT NULL,            -- 'user' | 'assistant', НЕ system/OOC
    text TEXT NOT NULL,
    created_at TEXT NOT NULL,
    sequence_index INTEGER NOT NULL  -- для сортировки внутри чата
);

CREATE VIRTUAL TABLE chat_messages_fts USING fts5(
    text, content='chat_messages', content_rowid='rowid'
);
```

### 2.2 Логика "горячего буфера"
- Последние 4 сообщения чата живут только в памяти приложения / временной структуре,
  не пишутся в `chat_messages` сразу.
- При поступлении 5-го нового сообщения — самое старое из буфера "остывает" и переносится
  в `chat_messages` с присвоением постоянного UUID.
- OOC-сообщения (определяются так же, как в `extract_for_backfill` — префиксы `OOC:`, `(OOC`)
  и системные — не попадают в буфер вообще, фильтруются на входе.
- Нужно решить отдельно: что считать "чатом" для этого буфера — весь диалог или per-character
  срез. Скорее всего per `chat_id` + `character_id`, как и остальная система.

### 2.3 Риск, который не закрывается полностью
Свайп/редактирование сообщения, которое уже "остыло" и попало в `chat_messages`, оставит
битую ссылку (raw-текст не будет совпадать с тем, что сейчас в SillyTavern). Это принятый
риск буфера на 4 сообщения — он не страхует от редактирования в глубине истории, только
от частых свайпов последних реплик.

## Этап 3 — Extraction по сцене целиком (заменяет построчную regex-классификацию)

### 3.1 Триггер extraction
Переиспользовать логику накопления, аналогичную текущему `summary_service.py`
(`DEFAULT_SUMMARY_WINDOW`), но как триггер для extraction, а не только для summary.

### 3.2 LLM extraction со structured output
- Переписать логику из удалённого `llm_extractor.py`, но с нормальным structured output
  (`response_format=json_schema`, если провайдер поддерживает — DeepSeek/OpenRouter обычно да),
  вместо хрупкого `re.search(r"\{[^{}]*\}")`.
- На вход — вся сцена (буфер сообщений), не одна реплика.
- На выходе — факты (что изменилось), а не пересказ/сырой текст. Это меняет суть того, что
  хранится: сейчас `content = truncate_content(text)` хранит обрезанный сырой текст,
  должно стать "извлечённый факт".

### 3.3 Привязка к raw-сообщениям
- Каждый извлечённый факт получает `source_message_ids: list[str]` — ссылки на UUID
  сообщений из `chat_messages` (Этап 2), из которых факт извлечён.
- Это требует, чтобы момент extraction видел оригинальные message_id — значит extraction
  должен запускаться **после** того, как сообщения остыли в raw-таблицу, либо буфер должен
  передавать id вместе с текстом даже до остывания.

### 3.4 Regex как дешёвый pre-filter, не как единственный классификатор
- Текущие regex-маркеры не выбрасываются полностью — используются как первый фильтр
  "стоит ли вообще звать LLM на этот батч", чтобы не тратить API-вызовы на пустые обмены.
  Финальная классификация и извлечение факта — за LLM.

## Этап 4 — Консолидация: схлопывание, а не накопление

### 4.1 Текущее состояние (после ревью summary_service.py)
- `summary_source_memory_ids` уже сохраняется в metadata — ссылки memory→summary уже есть.
- Цепочка обрывается на шаге memory→raw, потому что extraction (Этап 3 до доработки)
  не сохраняет message_id вообще.
- `generate_rolling_summary` и `generate_tiered_consolidation` создают **новую summary-запись**
  или обновляют существующую (`update_memory`) — обновление есть, это хорошо, но нет логики
  именно слияния противоречащих фактов ("Марк врач" → "Марк работает в новой больнице"
  должно заменить факт, а не просто попасть в текст следующего summary как ещё одна строка).

### 4.2 Что добавить
- При консолидации: расширить `_build_summary_metadata`, чтобы агрегировать
  `source_message_ids` transitively через все memory, попавшие в summary
  (summary → memories → raw messages).
- Явная логика обнаружения конфликтующих/обновляющих фактов про одну и ту же сущность
  перед тем, как звать LLM на консолидацию — иначе LLM просто сворачивает текст,
  не обязательно разрешая противоречия осмысленно.

### 4.3 Eval как обязательный гейт
- `run_retrieval_eval.py` — прогон в CI на каждый PR, затрагивающий extraction/consolidation/
  retrieval-логику. Без golden-датасета (нужно проверить, есть ли он уже в скрипте) —
  собрать минимальный набор пар запрос→ожидаемый факт вручную, на основе существующих
  verification-отчётов в `docs/`.

## Этап 5 — Retrieval fallback на raw-историю

### 5.1 Confidence score
- Текущий `retrieve_service.py` не считает явный confidence/score уверенности ответа —
  нужно добавить агрегированную метрику (например, top score из гибридного ранжирования
  ниже порога = низкая уверенность).
- Порог калибруется через eval-датасет (Этап 4.3), не на глаз.

### 5.2 Триггеры fallback (оба варианта, как уточнено)
- **Автоматический:** если top retrieval score ниже порога — дополнительно делать FTS5-запрос
  по `chat_messages_fts` и возвращать сырые совпадения с пометкой "из raw-истории".
- **Ручной:** отдельный эндпоинт/UI-команда "показать детали" — принимает `memory_id`,
  достаёт связанные `source_message_ids` через цепочку memory→raw, возвращает оригинальный
  текст сообщений.

### 5.3 Маркировка происхождения в ответе
Любой результат, пришедший из raw fallback, должен быть явно помечен как "не из
консолидированной памяти" — чтобы было видно качество источника при использовании
в SillyTavern-промпте.

## Порядок выполнения (сводка)

1. Этап 1 — чистка долга (дублирование, мёртвый код, конфиг весов, security, async fix)
2. Этап 2 — raw-таблица сообщений + горячий буфер на 4 сообщения
3. Этап 3 — extraction по сцене с structured output + привязка к message_id
4. Этап 4 — консолидация со слиянием фактов + transitively-агрегированные source_message_ids
5. Этап 5 — confidence score + автоматический/ручной fallback на raw FTS

Каждый этап ломает существующие тесты в разной степени — после Этапа 1 тесты должны
проходить как раньше (рефакторинг без изменения поведения). После Этапов 2–5 потребуется
писать новые тесты под новую логику, старые тесты на `extract_memories`/`extract_for_backfill`
придётся переписать под объединённую функцию с режимом.

## Важно: `/clear` между этапами в Claude Code

Каждый этап — отдельная сессия Claude Code с `/clear` перед началом следующего.

- Этапы крупные и затрагивают разные части кодовой базы — тащить историю предыдущего
  этапа в следующий только раздувает контекст и расход токенов без пользы.
- Перед `/clear` — зафиксировать результат (commit, или хотя бы краткое резюме что сделано
  и что осталось) в файле/CLAUDE.md, чтобы не держать это в истории чата ради памяти.
- Внутри одного этапа `/clear` не нужен, если работа идёт непрерывно — но если откроется
  посторонняя задача (например, починка несвязанного бага) — это тоже повод для `/clear`
  до возврата к плану.
- Если в процессе этапа понадобится Opus для сложного архитектурного решения (например,
  схема consolidation в Этапе 4) — переключиться через `/model`, не открывать для этого
  отдельную сессию с нуля.
