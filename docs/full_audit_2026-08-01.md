Подтверждено запуском:

```
GROUP SUMMARIES: [{... 'total_count': 3, 'stable_count': 2, 'episodic_count': 1 ...}]
   ← при 1 реальной памяти и 2 трекерах
AFTER DELETE-CHAT -> remaining trackers: [('tracker', 'timeline')]
```

Три отдельные находки:

1. **`list_chat_group_summaries` не фильтрует трекеры.** Они попадают в
   `total_count` и, поскольку у трекеров `layer='stable'`, ещё и в
   `stable_count`. Сайдбар UI завышает число «стабильных воспоминаний» на
   число трекеров чата (в живой БД трекеров 8). Единственный запрос к
   `memories`, где §4 спеки не выполнен.

2. **Удаление чата оставляет трекеры сиротами.** Оба пути удаления
   (API и UI) перебирают `list_memories(...)`, который трекеры скрывает —
   поэтому строки трекеров переживают «Delete ALL memories for this chat».
   Если чат с тем же `chat_id` появится снова, он унаследует протухшие
   таймлайн/отношения от предыдущего.

3. **Экспорт теряет трекеры.** `/ui/export` тоже идёт через `list_memories`,
   так что трекеров в `.jsonl` нет. Импорта в коде нет вообще, но при
   ручном восстановлении из экспорта трекеры пропадут молча.

Замечание по последней строке таблицы: `get_memory_by_id` типа не проверяет, и
универсальные роуты (`DELETE /memory/{id}`, `/ui/{id}/pin`) примут id трекера.
На практике id трекера в UI не видно (карточки трекеров рендерит отдельная
вкладка), так что путь не достижим кликом — но через API достижим.

## 3. `retrieve.user_input_preview` — баг или ожидаемое поведение?

**Причина (из кода):** проверена по исходникам SillyTavern в
`~/SillyTavern/public/script.js` — не по предположению.

Внутри одного вызова `Generate()`:

| Строка `script.js` | Событие |
|---|---|
| 4240 | `emit(GENERATION_STARTED, …)` ← хук расширения |
| 4262 | `emit(GENERATION_AFTER_COMMANDS, …)` ← хук расширения |
| **4394** | **`await sendMessageAsUser(textareaText, …)`** ← текущее сообщение попадает в `chat` |

Оба хука, на которые реально подписывается расширение
(`audit.mjs:8` `PRE_GENERATION_HOOK_CANDIDATES`), срабатывают **до** того, как
текущее сообщение пользователя добавлено в массив `chat`. `getLastUserMessage()`
(`main.mjs:310`) идёт по `chatContext.chat` с конца — и находит **предыдущее**
сообщение.

Третий кандидат из списка, `GENERATE_BEFORE_COMBINE_PROMPTS` (строка 5175),
срабатывает уже после 4394 и видел бы правильный текст — но он лежит внутри
`getCombinedPrompt()`, т.е. в ветке text-completion, и на chat-completion
API (nano-gpt/DeepSeek, как здесь) не эмитится вовсе.

Отдельно: комментарий в `main.mjs:812–829` описывает ровно этот эффект, но
трактует его как проблему **только dry-run прохода**. `isDryRun()` отсекает
dry-run — а на реальном проходе состояние `chat` точно такое же устаревшее.
Гард от dry-run эту причину не устраняет.

**Баг или ожидаемое поведение (окно контекста)?** — **Баг.** Это не «окно
контекста на N последних сообщений», а сдвиг на один ход: и `user_input`, и
`recent_messages` формируются из состояния чата *до* текущей реплики.

**Если баг — влияет ли на качество retrieval-скоринга?** — **Да, напрямую.**
`user_input` — основной вход скоринга: `retrieve_service` строит по нему
keyword-overlap, entity-overlap и relationship-cue-overlap (веса
`KEYWORD_WEIGHT`/`ENTITY_WEIGHT`/`RELATIONSHIP_CUE_WEIGHT`). Запрос уходит по
предыдущей реплике, т.е. память подбирается под прошлый ход. Приведённый в
шаблоне пример (`preview` = «*кладу руки под её попку*» при отправленном «Как
ты себя чувствуешь?») — это не косметика превью: сервер действительно искал по
первой строке. Усугубляется хардкодом `getRecentMessagesForRetrieve(3)` из §1 —
контекстное окно тоже сдвинуто и вдобавок урезано до 3.

**Серьёзность:** **высокая** — это самый значимый функциональный дефект из
найденных. Затрагивает каждый ход каждого чата, тихо и без ошибок в логе.

## 5. Архитектурная целостность после сегодняшних добавлений

**Идемпотентность миграций** — да, все три безопасны для повторного прогона.
Проверено чтением `app/db.py:155–314`:

- каждая закрыта пробой состояния, а не флагом версии: `_needs_summary_migration`
  и `_needs_tracker_migration` читают текст CHECK-констрейнта из `sqlite_master`,
  `_needs_chat_messages_normalized_text_migration` — `PRAGMA table_info`. На уже
  мигрированной БД проба возвращает `False`;
- все три обёрнуты в `SAVEPOINT` с `ROLLBACK TO` + `raise` — частично применённая
  миграция невозможна;
- все `CREATE` — с `IF NOT EXISTS`;
- порядок в `init_schema` корректен: `summary` → `tracker` →
  `chat_messages.normalized_text`, и комментарий на 301–302 верен (после
  summary-миграции таблица пересоздаётся из `MEMORIES_TABLE_SQL`, где `tracker`
  уже есть, поэтому вторая проба даёт `False`);
- `_run_chat_messages_normalized_text_migration` отдельно обосновывает
  `ALTER TABLE ADD COLUMN` вместо rename/copy — из-за external-content FTS5,
  привязанного к `rowid`. Обоснование корректное.

Одно замечание, не про идемпотентность: обе rename/copy-миграции копируют
жёсткий список из 16 колонок. На БД старее самой старой поддерживаемой схемы
`SELECT` упадёт → `ROLLBACK` → `raise` → сервер не стартует. Поведение
безопасное (данные целы), но диагностика будет непонятной.

**Порядок эндпоинтов** — да, нарушений нет. В `memory_api.py` все именованные
роуты (`/create`, `/list`, `/store`, `/retrieve`, `/keys`, `/clip`, `/summarize`,
`/consolidate`, `/trackers`, `/tracker/update`, `/backfill`, `/scene`,
`/chat/{chat_id}`, `/models`, `/provider`) объявлены на строках 48–503, а
catch-all `/{id}` — на 503–545. В `ui.py` то же: именованные 442–719, затем
`/ui/{memory_id}/*` 755–820. Плюс есть `tests/test_route_ordering.py`.

код правился до 17-го):

## 6. Безопасность данных

| Место в коде | Операция | Есть ли защита? |
|---|---|---|
| **`app/main.py:25–27`** | `init_schema()` (включая rename/copy/**DROP TABLE**) выполняется **до** `run_backup()` | ❌ **нет** — снимок делается уже после миграции |
| `app/services/backup_service.py:58–62` (`rotate_backups`) | Удаление бэкапов по счётчику (`BACKUP_KEEP=14`), не по возрасту | ⚠️ частично |
| **`chat_messages`** | — | ❌ **пути удаления не существует вовсе** |
| `DELETE /memory/chat/{chat_id}`:441 | Удаление всех записей чата по HTTP | ⚠️ подтверждения/dry-run нет; `character_id` необязателен → без него сносит чат по всем персонажам |
| `POST /ui/delete-chat`:609 | То же из UI | ✅ `onsubmit="return confirm(...)"` в `_scope.html:23` |
| `POST /ui/{id}/delete`:811 | Удаление одной записи | ✅ `confirm()` в `_memory_list.html:81` |
| `DELETE /memory/{id}`:539 | Удаление одной записи по API | ⚠️ подтверждения нет (ожидаемо для API) |
| `upsert_tracker`:646 | Перезапись документа трекера целиком | ⚠️ истории нет; страховка — только суточный бэкап |
| Экспорт/удаление с `limit=10000` | см. §1 | ❌ молчаливое усечение |

Три содержательные находки:

1. **Бэкап снимается после миграции схемы, а не до неё.** В `lifespan`
   порядок: `validate_security()` → `init_schema()` → `run_backup()`.
   `init_schema` — единственное место, где выполняется `DROP TABLE`
   (в `_run_summary_migration:237` и `_run_tracker_migration:276`). Если
   миграция потеряет строки, единственный снимок «до» будет затёрт снимком
   «после». Savepoint защищает от сбоя *внутри* транзакции, но не от
   логической ошибки в самом `INSERT … SELECT`. Правильный порядок —
   `run_backup()` перед `init_schema()`.

2. **`chat_messages` невозможно удалить.** В `chat_message_repo.py` восемь
   функций: вставка, поиск, выборка, FTS — **ни одной удаляющей**. Поиск по
   всему репозиторию и тестам: `DELETE FROM chat_messages` не встречается
   нигде. Следствия: (а) «Delete ALL memories for this chat» удаляет
   производные факты, но оставляет исходный сырой текст, который дальше
   остаётся доступен через FTS-фоллбэк ретрива; (б) таблица растёт
   безостановочно — сейчас 4150 строк, 37.2 МБ данных + 21.8 МБ индекса, при
   среднем сообщении 2778 символов.

3. **Ротация бэкапов по количеству, а не по возрасту.** Сейчас `data/backups/`
   ровно на пределе: 14 файлов, суточный cron в 01:00 UTC плюс снимки на
   старте. Отладочная сессия с 14 перезапусками вытеснит **всю** суточную
   историю за один вечер, и обнаружится это только когда бэкап понадобится.
   Учитывая, что 9 из 14 файлов по 60 МБ и один по 77 МБ — каталог весит
   ~862 МБ на телефоне.

## 7. Мнение и рекомендации (не факты — субъективная оценка)

**Оптимизация производительности:**

- `idx_chat_messages_normalized (chat_id, character_id, normalized_text)` —
  **21.8 МБ из 77 МБ базы (28%)**. Индекс включает целиком колонку
  `normalized_text` со средней длиной 2609 символов, то есть хранит вторую
  полную копию всех сообщений. Нужен он только для точного сравнения при
  дедупликации. Индекс по хэшу (`normalized_hash` = 32–64 байта на строку)
  дал бы то же самое примерно за 0.3 МБ. Самая крупная одиночная экономия в
  проекте, и она чисто механическая.
- `LLM_TIMEOUT=30` при **26.4% фоллбэков** экстракции (568 неудач на 1583
  успеха) и 200 `ReadTimeout` в логе. У трекеров уже стоит
  `TRACKER_LLM_TIMEOUT=120`. Сценовой экстракции — рассуждающей модели по
  целой сцене — 30 секунд явно мало. Поднять до 60–90 секунд, вероятно,
  вернёт большую часть этой четверти.
- База 77 МБ на 4394 факта и 4150 сообщений. `VACUUM` после перехода на
  хэш-индекс должен сбросить её примерно вдвое.

**Архитектурные улучшения** (зная постфактум то, что известно сейчас):

- Хуки предгенерации оказались неподходящим местом для ретрива: они
  срабатывают до того, как SillyTavern запишет реплику в `chat` (§3). Реплику
  надо брать не из состояния чата, а из аргументов события — либо перехватывать
  на `MESSAGE_SENT`, кэшировать текст, и уже на хуке генерации использовать
  кэш. Это лечит причину, а не симптом, и попутно снимает потребность в
  гарде dry-run.
- Трекеры лежат в таблице `memories`, и почти вся работа с ними — это
  напоминание всем 13 запросам, что трекер не память. Изоляция работает
  (§2 — 11 путей из 14 фильтруют корректно), но держится на дисциплине: каждый
  новый запрос по умолчанию **неправильный**, пока автор не вспомнит про фильтр.
  Ровно так и появилась дыра в `list_chat_group_summaries`. Отдельная таблица
  `trackers` сделала бы неверный вариант непредставимым.
- Инвариант «не смешивать трекеры с памятью» стоит зафиксировать одним тестом,
  который перебирает функции репозитория рефлексией и требует, чтобы каждая
  либо фильтровала `type='tracker'`, либо стояла в явном списке исключений.
  Тогда дыры такого рода закрываются один раз, а не по одной.

**Технический долг:**

- Мокирование `list_retrieval_candidates` и `list_chat_group_summaries` в
  тестах (§4) — самый дорогой долг: оно не просто снижает покрытие, оно
  выдаёт зелёный сигнал на сломанном коде. Хотя бы по одному тесту против
  настоящей БД на каждую функцию репозитория.
- Приоритет legacy-плоских ключей в `settings.mjs:133–157` — временное решение,
  которое пережило свой повод. Для `memoryServiceUrl` его уже осознанно
  выключили; остальные поля остались в старом режиме скорее по инерции, чем
  по замыслу. Либо выключить везде, либо задокументировать, почему URL — особый.
- `getRecentMessagesForRetrieve(3)` — клиентская константа там, где в настройках
  уже есть `recentMessagesCount`. Классическая клиентская обрезка вместо
  серверной: сервер получает 3 сообщения и не знает, что их урезали.
- Каталог `docs/` — 19 файлов отчётов о ручных проверках (`live_st_*`,
  `lorebook_*`, `*_recheck_*`). Это журнал сессий, а не документация; полезное
  из него стоит поднять в `README`, остальное — в архив.
- `CLAUDE.md` (§5) — не просто устарел, а содержит **опасную** инструкцию
  удалить живой код. Это первое, что стоит поправить, потому что этот файл
  автоматически читает каждая следующая сессия.

**Риск избыточной сложности:**

Тревога уместна, но код её не подтверждает. 13.4 тыс. строк, 45 тестовых
файлов и 377 проходящих тестов на один телефон и одного пользователя — это
много по любым меркам. Но конкретные признаки «сложности ради сложности» не
находятся: разделения слоёв соблюдены, а комментарии в коде на удивление
дисциплинированны — почти каждое неочевидное решение объяснено вместе с
**поводом**, который к нему привёл (`audit.mjs:408–421` про ключ хода,
`db.py:164–179` про FTS-триггеры, `conftest.py:12–31` про негерметичные тесты,
`settings.mjs:166–173` про двойную нормализацию). Такие комментарии не пишут в
запутанном проекте — их пишут там, где сложность вынужденная и её осознают.

Реальный риск — не в объёме, а в **дисперсности**: два клиента к одному API
(`index.js` и `ui.py`), два формата настроек (плоский и вложенный), две копии
расширения на диске, два вида консолидации (rolling и tiered, причём rolling
де-факто не используется — ноль записей в БД). Каждая пара — это место, где
половина тихо расходится с другой. Из десяти находок этого аудита минимум
четыре живут именно на таких стыках.

Если сокращать — не функциональность. Сократить дубликаты: один формат
настроек, один путь консолидации, одна копия расширения.

## Итоговая сводка

**Критичные находки (влияют на данные):**

1. Бэкап снимается **после** миграции схемы (§6.1) — единственный снимок «до»
   затирается снимком «после», ровно в тот момент, когда он нужен.
2. `chat_messages` невозможно удалить ничем (§6.2) — удаление чата не удаляет
   сырой текст, и он остаётся доступен ретриву; таблица растёт без ограничений.
3. Удаление чата оставляет трекеры сиротами (§2.2) — новый чат с тем же id
   унаследует чужие таймлайн и отношения.
4. `/ui/export` не выгружает трекеры (§2.3) — при восстановлении из экспорта
   они теряются молча.

**Находки средней важности (влияют на корректность):**

5. **Ретрив спрашивает по предыдущей реплике** (§3) — затрагивает каждый ход
   каждого чата. По воздействию это находка №1 в аудите; в «данные» не
   попадает только потому, что ничего не разрушает.
6. Окна `limit=50` в консолидации (§1) — «сконсолидируй арку» видит 50 из 414
   записей; rolling-саммари продублируется вместо обновления.
7. Утечка трекеров в `list_chat_group_summaries` (§2.1) — сайдбар завышает
   `total_count` и `stable_count`.
8. Ложно-зелёные тесты из-за моков репозитория (§4) — не дефект сам по себе,
   но причина, по которой №7 дожил до аудита.
9. `recentMessagesCount` не влияет на ретрив (§1) — настройка ничего не
   делает, а аудит показывает конфиг вместо фактического значения.
10. `CLAUDE.md` предписывает удалить живой код (§5).

**Косметические находки:**

11. Асимметрия `??`/`||` в `settings.mjs` (§1).
12. Молчаливый пропуск битых строк backfill (§1).
13. `limit=10000` без сигнала о достижении потолка (§1).
14. `NULL != 1` в SQL групповых сводок (§1) — сейчас дремлет.
15. Ротация бэкапов по счётчику, а не по возрасту (§6.3).

**Рекомендуемый порядок исправления:**

Сначала — то, что дёшево и защищает от последствий всего остального:

1. **`CLAUDE.md`** (§5). Одна правка файла, никакого риска. Первым — потому
   что его читает каждая следующая сессия, и сейчас он предлагает удалить
   работающий код.
2. **Порядок бэкапа и миграции** в `main.py` (§6.1). Перестановка двух строк.
   Вторым — потому что дальше идут правки схемы и данных, и снимок «до»
   должен работать раньше, чем он понадобится.
3. **Ротация бэкапов по возрасту** (§6.3) — вместе с №2, тот же файл-сосед.

Затем — то, что видит пользователь на каждом ходу:

4. **Устаревшая реплика в ретриве** (§3). Самая ценная правка аудита.
   Отдельной сессией: нужен живой прогон в SillyTavern, юнит-тестом это не
   проверяется. Вместе с ней — `recentMessagesCount` (№9), это соседняя строка.
5. **Окна `limit=50` в консолидации** (§1). Тот же приём, что уже применён к
   чекбоксам UI, — брать полный пул.

Затем — целостность данных:

6. **Единая уборка чата**: удаление чата должно сносить трекеры и
   `chat_messages` (§6.2, §2.2). Здесь же добавить функцию удаления в
   `chat_message_repo`.
7. **Экспорт с трекерами** (§2.3) — рядом с №6, та же тема сохранности.
8. **Фильтр трекеров в `list_chat_group_summaries`** (§2.1) — одна строка,
   но только **вместе с тестом против настоящей БД**, иначе повторится.

Затем — фундамент, чтобы не пришлось делать это снова:

9. **Тесты против реальной БД** для `list_chat_group_summaries` и
   отбора кандидатов (§4), плюс рефлексивный тест инварианта трекеров.
10. **Хэш-индекс вместо полнотекстового** + `VACUUM` (§7) — минус ~21 МБ.
11. **`LLM_TIMEOUT`** до 60–90 секунд (§7) — одна переменная в `.env`,
    потенциально возвращает четверть проваленных экстракций.

Остальное (№11–14) — попутно, когда рядом будет открыт тот же файл.
